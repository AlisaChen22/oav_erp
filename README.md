# OAV ERP 庫存管理系統

PWA（手機可安裝、斷線可重傳）＋ SQL Server。**商業邏輯全部在 T-SQL**，前端只負責畫出 SQL Server 給的定義、以及離線佇列。

## 架構
```
手機/瀏覽器 (PWA)  ──POST /api {JSON}──▶  server.py（純轉送）──▶  EXEC api.呼叫 @請求
   web/ 通用畫面                            無商業邏輯               SQL Server oav37：全部邏輯
```
| 由 SQL Server 負責 | 物件 |
|---|---|
| 資料正確性 | 主鍵、外鍵、CHECK（含 期初+入-出=期末、在手+供給-需求=可用） |
| 過帳機制 | 25 個觸發程序：回寫出貨/退回/收貨/入庫/已領量、庫存異動、每日庫存餘額、在途、每日供需餘額 |
| 商業檢核 | 超量出貨/收貨/領料、負庫存、客戶/廠商/物料不符、倉庫不屬於單據工廠 |
| 報表 | 視圖、樞紐分析資料表函數（PIVOT）、過帳驗證視圖 |
| 畫面定義 | 欄位、型別、必填、主鍵、下拉選項、唯讀、報表參數 —— 全部取自系統目錄 |
| API | `api.呼叫`：功能表 / 定義 / 查詢（含多層鑽取）/ 讀取 / 存檔 / 刪除 / 選項 / 拷貝來源 / 拷貝；自動編號；冪等重送 |

新增資料表或欄位時，前端**不必修改**。

## 安裝與啟動
```
pip install pyodbc
copy config.example.json config.local.json   # 填入 SQL Server 連線（此檔不進 git）
python deploy.py --reset                      # 建立/重建資料庫 oav37 並載入範例資料（會清空資料！）
python verify.py                              # 驗證準則，全部「通過」才正確
python server.py                              # http://localhost:8000
```

|---|---|
| 訂單出貨明細.出貨數量 | 客戶訂單明細.出貨數量（訂單編號+訂單項次） |
| 出貨退回明細.退回數量 | 客戶訂單明細.退回數量（訂單編號+訂單項次） |
| 採購收貨明細.收貨數量 | 廠商採購明細.收貨數量（採購編號+採購項次） |
| 收貨退回明細.退回數量 | 廠商採購明細.退回數量（採購編號+採購項次） |
| 工單入庫明細.入庫數量 | 生產工單主檔.入庫數量（工單編號） |
| 工單領料明細.領料數量 | 生產工單明細.已領用量（工單編號+物料編號） |
| 8 種庫存單據 | 庫存異動明細 → 每日庫存餘額 |
| 訂單、採購、工單、預留、庫存 | 庫存在途明細 → 每日供需餘額 |

## 多層鑽取：每日庫存餘額
功能表「IM 庫存 → 每日庫存餘額」分三層，點選一列進入下一層：
1. **物料資料維護** → 點物料
2. **每日庫存餘額**（該物料各倉庫逐日 期初/入庫/出庫/期末）→ 點某一天
3. **庫存異動明細**（該物料、該倉庫、該日的每一筆異動單據）

層級、物件、過濾對應、排序都存在 `api.鑽取層級`，前端只是依定義一層層畫出來。

## 單據拷貝：從已訂未出明細建立出貨
在「訂單出貨維護」新增或修改時，按「從已訂未出明細拷貝」：
- 列出未出數量 > 0 的訂單項次；表頭已填客戶/銷售組織時只列該客戶的。
- 勾選後拷貝：自動帶入表頭的銷售組織、客戶編號，明細帶入 訂單編號、訂單項次、物料編號，出貨數量 = 未出數量（可再修改），再填倉庫即可存檔。
- SQL 端檢核：勾選的訂單必須同一客戶、與表頭一致；已在明細中的項次不會重複拷貝；數量以資料庫當下的未出數量為準。
- 「採購收貨維護」同樣可「從已採未交明細拷貝」。

對應設定存在 `api.拷貝來源`，拷貝邏輯在 `api.p_拷貝`。

## 樞紐分析
- **訂單出退分析**：`dbo.訂單出退樞紐(@年度)`，來源 `訂單出退分析` = 訂單出貨明細 UNION ALL 出貨退回明細。縱軸客戶編號、橫軸 01～12 月，統計 出貨數量、退回數量、出貨+退回，另有全年合計。
- **採購收退分析**：`dbo.採購收退樞紐(@年度)`，同上，縱軸廠商編號，統計 收貨數量、退回數量、收貨+退回。
- 畫面上的「年度」輸入框由 SQL 的函數參數自動產生，預設今年。

## 驗證準則
`dbo.驗證結果`（功能表「系統驗證 → 過帳驗證結果」或 `python verify.py`）逐條檢查 11 項，包含：
六項過帳累加、每日庫存餘額逐列 `期初數量+本期入庫-本期出庫=期末數量`、
每日供需餘額逐列 `在手數量+供給入庫-需求入庫=可用數量`、庫存帳與單據一致、在途與未結單據一致。
兩個逐列公式另以 CHECK 條件強制，不可能寫入不平衡的資料。

## 離線重傳
1. 每次存檔/刪除先寫入手機的待上傳佇列，帶一個 UUID `請求編號`。
2. 有網路立即送出；斷線、逾時或資料庫連不上（HTTP 503）時留在佇列，恢復連線、切回 App 或每 20 秒自動重送。
3. `api.請求紀錄` 保證同一請求編號只執行一次，重送不會重複入帳。
4. 資料錯誤（例如庫存不足）不重試，列在右上角 ⇅ 的「重傳失敗」清單。
5. 讀過的列表、單據、定義都會快取，離線時仍可查看。

> Service Worker 只在 **https** 或 **localhost** 生效；手機正式使用請在 server.py 前加 HTTPS 反向代理（IIS / nginx）。

## 與原規格的差異
- `生產工單主檔` 新增 **物料編號**（生產料號）；建立工單時依用量清單自動展開 `生產工單明細`。
- `客戶訂單明細`、`廠商採購明細` 新增 **工廠代碼**：每日供需餘額依「物料編號＋工廠代碼」計算，訂單與採購必須知道是哪個工廠的需求/供給；出貨/收貨的倉庫必須屬於該工廠。
- 出貨/退回/收貨/入庫明細的 `物料編號` 可空白，由來源單據自動帶入。
- 另加「現有庫存查詢」與「過帳驗證結果」。
